PoE Trade Bookmark(`v0.6.0`)에서 **되돌리기 어렵거나, 나중에 "왜 이렇게 했지?"라는 물음이
나올 결정**만 모은 문서입니다. 무엇을 해야 하는가는 [요구사항 명세](../REQUIREMENT.md)에,

무엇을 포기했는지를 적습니다.

## ADR-001. 크롬 사이드 패널 API를 버리고 거래소 페이지 안에 사이드바를 심는다

**상태**: 채택 (구현됨)
**요구사항**: FR-PANEL-01·02·03·04, NFR-SEC-01, NFR-ROB-05
**맥락**: 0.3.0까지는 크롬 사이드 패널(`sidePanel` 권한)이었습니다. 사이드 패널은 브라우저 창에
붙어 있어 탭을 옮겨도 계속 떠 있고, 거래소를 벗어난 자리에서는 방해만 됐습니다. 거래소를 보면서
동시에 조작해야 하므로 툴바 팝업도 답이 아닙니다.
**결정**: 콘텐츠 스크립트로 페이지에 심고, 거래소를 떠나면 함께 사라지게 합니다. 화면 오른쪽 끝의
세로 손잡이로만 열고 닫습니다(`panel.js:1-7`, `225-244`). 열면 덮지 않고 밀어내며, 문서에 손대는
것은 `<html>`의 `margin-right` 하나뿐입니다 — 거래소 margin을 이기도록 `!important`로 얹습니다
(`panel.js:215-223`). 폭 `min(360px, 50vw)`는 한 곳에서만 정합니다(`panel.js:21-23`).
**근거**: 전환 커밋 `958a485`가 이유를 그대로 적고 있습니다 — "크롬 사이드 패널은 탭을 옮겨도 계속
떠 있어서 거래소 밖에서는 방해가 됐다". 같은 커밋에서 `permissions`가 `["storage", "sidePanel"]` →
`["storage"]`로 줄고 `host_permissions`가 사라졌으며 `minimum_chrome_version`이 114에서 102로
내려갔습니다. UI 결정인 동시에 권한 축소 결정이었습니다.
**결과**: 목록 항목은 언제나 **현재 탭**에서 이동합니다(`panel.js:288-293`). 주소 추적을 스스로 해야 해
`popstate`/`hashchange` + 0.5초 폴링이 들어왔고(`panel.js:681-693`, FR-SPA-01), 페이지가 바뀔 때마다
스크립트가 다시 시작되는 것도 이 결정의 대가입니다(ADR-006).
**대안**: 사이드 패널 유지(탭 전역이라 밖에서 방해), 툴바 팝업(보면서 조작 불가), 오버레이(화면을 가림).

## ADR-002. 사이드바는 Shadow DOM 안에서 그리고, 스타일은 코드로 만든 시트로 넣는다

**상태**: 채택 (구현됨)
**요구사항**: FR-PANEL-07·08·09, NFR-ROB-05
**맥락**: 페이지 안에 UI를 심으면 거래소 CSS와 서로를 오염시킵니다. 거래소는 CSP를 걸고 있어
`<link>`나 `<style>`이 `style-src`에 막힐 수 있고, 전역 단축키도 듣고 있어 패널 입력칸에 친 글자가
거래소 동작을 일으킬 위험이 있습니다.
**결정**: 호스트 `div`를 `documentElement`에 붙이고 `attachShadow({ mode: 'open' })` 안에서만
그립니다(`panel.js:151-168`). `panel.css`는 `chrome.runtime.getURL`로 읽어 `CSSStyleSheet`를 만든 뒤
`adoptedStyleSheets`로 붙이고(`panel.js:170-186`), 호스트에서 `keydown`/`keyup`/`keypress`를
`stopPropagation`으로 끊습니다(`panel.js:188-191`).
**근거**: 코드로 만든 스타일시트는 문서가 로드하는 리소스가 아니라 `style-src`의 영향을 받지
않습니다(`panel.js:170-174`). 실패해도 죽지 않도록 경고만 남기고 호스트를 다시 보이게 해 기능은
유지합니다(`panel.js:181-186`, FR-PANEL-09). `body`가 아니라 `documentElement`에 붙이는 것은 거래소가
`body`를 갈아끼울 수 있기 때문입니다(`panel.js:167`).
**결과**: `panel.css`가 `web_accessible_resources`에 올라가야 하고, 스타일 적용이 비동기라 초기화가
`applyStyles()`부터 시작합니다(`panel.js:1280-1281`). 그림자 밖은 격리가 닿지 않아 EN 단추만
`copy-en.css`를 페이지에 직접 주입합니다 — 유일한 예외입니다. 키를 끊었으므로 Esc도 그림자 안에서
직접 들어야 합니다(`panel.js:1011-1017`).
**대안**: iframe 격리(폼 DOM을 직접 읽어야 하는 ADR-003과 충돌), `<style>` 주입(CSP), 클래스 접두어(거래소
CSS가 패널을 건드리는 방향은 못 막음).

## ADR-003. 검색 조건은 요청 없이 페이지의 검색 폼(DOM)에서만 읽는다

**상태**: 채택 (구현됨)
**요구사항**: FR-SUM-01·02·03·07·08, NFR-API-03, NFR-ROB-01·02
**맥락**: 검색 조건은 주소에 담기지 않고 서버의 검색 ID에 묶여 있습니다. 알아보려면 API로 되묻거나
폼을 읽는 두 길뿐인데, 북마크 이름은 검색 결과를 볼 때마다 채워지는 값이라 API를 부르면 검색을 볼
때마다 요청 한도를 태우게 됩니다.
**결정**: 조건은 오직 폼 DOM에서 읽습니다. 마크업에 기대는 선택자는 `search-summary.js:22-25` 네 줄에
모아 두고, 사용자가 고르거나 입력한 값만 담습니다 — `modified`가 붙은 드롭다운·최소/최대 칸과 능력치
그룹입니다(`search-summary.js:97-130`). 폼이 아직 안 채워졌을 수 있어 0.25초 간격으로 8회까지 다시
읽습니다(`panel.js:481-505`).
**근거**: 패널은 거래소 페이지 안에서 도는 콘텐츠 스크립트라 요청 없이 폼을 읽을 수 있고
(`search-summary.js:1-5`), 실제로 이 경로에는 `fetch`가 한 줄도 없습니다(NFR-API-03). 능력치는 그룹
제목까지 함께 담습니다 — 같은 스탯이라도 `모두 일치`인지 `일치 없음`인지에 따라 뜻이 정반대라 제목을
빼면 요약이 거짓이 됩니다(`search-summary.js:156-177`).
**결과**: 거래소가 마크업을 바꾸면 손볼 곳이 `search-summary.js` 상단으로 한정됩니다(NFR-ROB-01). 못
읽어도 죽지 않고 검색 ID로 만든 이름(`trade-url.js:71-77`)과 주소 툴팁(`panel.js:303`)으로 물러서며,
대량거래는 폼 구조가 달라 요약이 비어 있습니다(REQUIREMENT §2.2). 조건이 같으면 같은 검색 ID가 오므로,
0.5초 주기로 폼에서 뽑은 이름이 달라졌는지도 봅니다(`panel.js:529-552`).
**대안**: `GET /api/trade/search/…`로 되묻기(화면을 볼 때마다 요청), 거래소 Vue 내부 상태 읽기(더 취약).

## ADR-004. 요약은 보여 줄 문구가 아니라 읽어 낸 구조 그대로 저장한다

**상태**: 채택 (구현됨)
**요구사항**: FR-SUM-10, FR-BM-07·10
**맥락**: 툴팁 요약의 표시 형식은 언제든 바뀔 수 있지만 북마크는 한 번 저장하면 오래 남습니다. 완성된
문자열을 저장하면 나중에 표기를 고쳐도 옛 항목은 옛 형식에 갇힙니다.
**결정**: 저장하는 것은 `{ item, filters, ranges, statGroups }` 구조이고(`search-summary.js:97-130`),
보일 문구는 그릴 때 `formatSummary`가 만듭니다(`search-summary.js:179-185`).
**근거**: `panel.js:436`("구조 그대로 넣어 둔다. 보여 주는 모양은 그릴 때 정한다")과 REQUIREMENT §6이
이유를 명시합니다. 같은 구조를 두 소비자가 다른 규칙으로 씁니다 — 툴팁은 14줄에서 자르고
(`search-summary.js:27-28`), 기본 이름은 80자에서 자르며 능력치를 개수로 접습니다
(`search-name.js:44-66`). 문자열로 저장하면 둘 다 만족할 수 없습니다.
**결과**: 스키마가 곧 저장 형식이 됩니다. `summary`가 옵셔널 필드라는 것과, 요약이 붙기 전에 저장한
북마크를 마이그레이션 없이 채워 넣는 방식은 [DESIGN.md](../DESIGN.md) §6에 있습니다.
**대안**: 완성된 문구 저장(표시 형식 변경에 갇힘), 열 때마다 다시 읽기(목록은 그 검색 페이지 밖에서도 보임).

## ADR-005. 정규화한 URL을 북마크·기록의 동일성 키로 삼는다

**상태**: 채택 (구현됨)
**요구사항**: FR-BM-03, FR-HIST-03·04·06, FR-SPA-03
**맥락**: 거래소는 조건이 같으면 같은 검색 ID를 돌려줍니다. 저장할 때마다 새 키를 매기면 같은 검색이
목록에 여러 번 쌓입니다. 주소에는 검색과 무관한 쿼리스트링·해시가 붙고, 언어 세그먼트
(`/kr/trade/...`)가 끼어들기도 합니다.
**결정**: `parseTradeUrl`이 쿼리스트링·해시를 버리고 끝의 `/`를 떼어 정규화한 주소를 만들고
(`trade-url.js:65-67`), 그 값이 곧 항목의 정체성입니다. 저장된 북마크는 URL로 찾고(`panel.js:588`),
같은 URL로 다시 저장하면 새 항목 대신 이름만 갱신합니다(`panel.js:641-652`). 기록도 같은 URL이면 맨
위로 올리며(`panel.js:417-443`) 최대 50개입니다(`panel.js:371-372`).
**근거**: `panel.js:414-415`가 이유를 직접 적습니다 — "거래소는 조건이 같으면 같은 검색 ID를 돌려주므로,
같은 검색을 반복해도 목록이 그것으로 채워지지 않는다". 50개는 저장 공간이 아니라 "목록에서 찾기 좋은
길이"가 기준입니다(`panel.js:371`).
**결과**: 같은 조건이라도 리그나 호스트가 다르면 다른 항목이 됩니다. 조건을 바꿔 재검색했는데 검색 ID가
그대로면 주소로는 변화를 알 수 없어 폼에서 뽑은 이름을 따로 봐야 합니다(ADR-003). 기록 항목은 `createdAt`
대신 마지막 검색 시각 `at`을 갖습니다(`panel.js:438`).
**대안**: 검색 ID만 키로 쓰기(호스트·리그가 섞여 충돌), 새 UUID(중복이 쌓여 FR-BM-03·FR-HIST-03에 어긋남).

## ADR-006. 상태는 `chrome.storage.local`에만 두고, 이동을 건너는 값에는 TTL을 붙인다

**상태**: 채택 (구현됨)
**요구사항**: FR-SPA-04, FR-HIST-02·08, FR-BUILD-08·11, FR-BM-09, FR-PRESET-06, NFR-API-04
**맥락**: 사이드바가 페이지 안에 있으므로(ADR-001) 이동할 때마다 스크립트가 다시 시작됩니다. 그런데 두
가지는 이동을 건너야 합니다 — 빌더가 만든 검색의 이름·정규식, 그리고 "이 이동은 사이드바에서 눌러 온
것"이라는 표식(기록에 남기면 안 되는 이동)입니다. 메모리에 두면 이동과 함께 사라집니다.
**결정**: 상태는 모두 `chrome.storage.local`에 둡니다. 이동을 건너는 값에는 수명을 붙입니다 — 빌더 결과
`pending`은 10분(`panel.js:724-726`, `774-788`), 이동 표식 `nav`는 60초이며 **한 번 쓰고 버리고 주소가
일치할 때만 소비**합니다(`panel.js:373-374`, `394-409`). 리그 목록은 origin별 24시간 캐시입니다
(`panel.js:888-903`). `sync`는 쓰지 않습니다.
**근거**: `takePanelNav`는 오래된 표식을 지우기만 하고 주소가 맞을 때만 값을 돌려줍니다 — "마침 같이
열린 다른 탭이 대신 써 버리지 않게" 하려는 것입니다(`panel.js:398-409`, FR-HIST-08). 소비 시점도 정해져
있어 초기화에서 첫 `refresh`보다 먼저 읽고(`panel.js:1292-1294`), 빌더는 이동 **전에** 결과를 맡기고
움직입니다(`panel.js:947-955`). `local`인 이유는 동기화를 비대상으로 정했기 때문입니다(REQUIREMENT §2.2).
**결과**: 북마크와 프리셋을 다른 컴퓨터로 옮길 방법이 없고 확장을 지우면 함께 사라집니다(REQUIREMENT §8,
[TODO.md](../../TODO.md)). TTL이 지난 값은 조용히 무시하되 지우지는 않고, 다른 탭과의 즉시 반영은
`storage.onChanged`가 맡습니다(`panel.js:696-716`).
**대안**: `chrome.storage.sync`(동기화가 비대상), 전역 변수(이동에서 소실), 표식을 URL 파라미터로(ADR-005와 충돌).

## ADR-007. 한글→영문 번역 대신 아이템 ID를 다시 묻고, 그 요청만 서비스 워커로 보낸다

**상태**: 채택 (구현됨)
**요구사항**: FR-EN-02·03·04·06·08, NFR-SEC-01·02, NFR-API-02
**맥락**: 거래소는 아이템 텍스트를 보고 있는 사이트의 언어로만 줍니다. 한국 서버에서는 문구가 전부
한글이라 PoB에 붙여넣을 수 없고, 사전을 만들어 옮기는 길은 스탯이 수천 줄이라 어긋나기 쉽습니다.
**결정**: 번역하지 않습니다. 아이템 ID가 realm·언어와 무관한 해시라는 점을 이용해 같은 ID를
`https://www.pathofexile.com/api/trade/fetch/<ID>`에 다시 묻고 GGG가 만든 문구를 그대로 씁니다
(`background.js:1-13`). 이 요청만 페이지와 다른 출처이고 거래소 API는 CORS 헤더를 주지 않으므로
`host_permissions`를 가진 서비스 워커가 대신 보냅니다. 요청에는 로그인 정보도(`credentials: 'omit'`,
`background.js:38-40`) 검색 ID도 붙이지 않습니다.
**근거**: "옮기는 과정이 아예 없기 때문"이 정확성의 근거입니다(`background.js:7-9`). 검색 ID를 빼는 이유는
한국 서버의 검색 ID가 영문 거래소에 없기 때문이고, 자격 증명을 빼는 이유는 필요가 없는 데다 한도가 계정이
아니라 IP로 잡히기 때문입니다(`background.js:31-33`, `45-49`). `extended.text`는 UTF-8을 base64로 감싼
값이라 `atob`만 쓰면 비ASCII가 깨지므로 `TextDecoder`로 한 번 더 풉니다(`background.js:18-25`).
**결과**: 이것 하나 때문에 `host_permissions: ["https://www.pathofexile.com/*"]`와 서비스 워커가 존재합니다
— ADR-001에서 지웠던 것을 EN 복사가 되살린 셈입니다(NFR-SEC-01). 영문 거래소에 없거나 내려간 매물은
실패하며 원인별로 알립니다(`background.js:45-76`). 요청을 아끼려고 아이템별 캐시와 진행 중 요청 합치기를
둡니다(`copy-en.js:30-32`, `39-62`, NFR-API-02).
**대안**: 한↔영 사전 내장(표기가 어긋남), 콘텐츠 스크립트에서 직접 `fetch`(CORS), 영문 거래소에서 재검색 안내
(검색 ID가 서버 간 호환되지 않음).

## ADR-008. 인게임 정규식은 `RegExp`가 아니라 게임 엔진을 흉내 낸 자체 엔진으로 해석한다

**상태**: 채택 (구현됨)
**요구사항**: FR-REGEX-03·05·06·07
**맥락**: 확장은 "이 정규식이 어느 모드를 거른다"를 표시하고 붙여넣은 정규식으로 모드를 역선택합니다. 판정이
게임과 어긋나면 확장만 믿고 산 지도를 창고에서 잃어버리는데, `RegExp`는 게임 엔진과 규칙이 다릅니다.
**결정**: `poe-regex.js`가 패턴을 직접 파싱·컴파일·매칭합니다. 게임과 맞춘 자리는 셋입니다. ① 언제나 한 줄
매칭 — 어떤 명령도 `\n`을 먹지 않고 `^`/`$`는 줄마다 걸립니다(`poe-regex.js:580-595`, `628-634`).
② 정규식 해석 전에 **글자 그대로 먼저** 찾습니다(`662-674`). ③ 인게임 고유 문법 — 공백은 AND, `!`는 항목
부정, `"…"`는 묶음(`33-81`). 게임에서 어떻게 되는지 알 수 없는 문법은 매칭에서 빼고 따로 알립니다
(`kind: 'unsupported'`, `137-152`).
**근거**: 게임 엔진이 MSVC `std::regex`(ECMAScript 문법)라는 판단은, 검색칸에서 튀어나온 예외 대화상자
문구가 microsoft/STL의 것과 한 글자도 다르지 않다는 관찰입니다(`regex_error(error_complexity)`,
https://www.pathofexile.com/forum/view-thread/3195613 — `poe-regex.js:14-18`). 한 줄 매칭의 근거는 GGG
포럼 글입니다(https://www.pathofexile.com/forum/view-thread/3305826 — "The regex engine always performs
a single line match … `(?m)` doesn't do anything", `20-25`). 리터럴 우선의 근거는 RhysGGG의 "try a basic
string match first, then attempt a regex match if the basic match fails"와 3.14.1c의 품질 `+` 검색
수정입니다(`662-670`). 전방 탐색과 `\d`가 통한다는 근거는 poe.re(veiset/poe-vendor-string)가 인게임에
붙여 넣게 하는 `(?=(\S*r){2})`이고(`154-158`, `283-294`), 후방 탐색은 MSVC에 구현이 없어 막습니다
(`296-298`). 역참조와 `\b`는 통했다는 보고를 찾지 못해 물러섭니다(`342-350`). 줄바꿈 없는 문구에서는
26개 패턴이 `RegExp`와 답이 같아야 한다는 대조 테스트도 있습니다(`test/poe-regex.test.js:226-261`).
**결과**: 문법을 넓히려면 파서와 컴파일러를 함께 고쳐야 합니다. 문법이 깨진 패턴은 오류로 막지 않고 글자
그대로 찾는 항목이 되며 `errors`에만 담깁니다(`poe-regex.js:689-718`). 모드 데이터 검증도 같은 엔진을
쓰므로(`trade-query.js:97-101`) 엔진의 판정이 곧 데이터 품질 기준이 됩니다(ADR-010).
**대안**: `new RegExp(pattern, 'im')`(게임에 없는 문법까지 통과), 게임 문법의 부분집합만 지원(FR-REGEX-03이 깨짐).

## ADR-009. 매칭은 되추적이 아니라 NFA 시뮬레이션으로 한다

**상태**: 채택 (구현됨)
**요구사항**: FR-REGEX-08, NFR-ROB-04
**맥락**: 모드 검색칸과 "정규식으로 선택" 칸에는 아무 정규식이나 붙여 넣을 수 있고(`panel.js:1203-1243`), 모드
검색은 글자를 칠 때마다 80개 모드 전체에 대고 돌아갑니다(`panel.js:808`). 되추적이면 한 패턴에 UI가 멈춥니다.
**결정**: 마디 나무를 명령 목록으로 옮기고, 실행 중인 자리를 집합으로 들고 글자를 한 번씩 훑는 NFA
시뮬레이션으로 맞춥니다(`poe-regex.js:410-431`, `597-658`). 전방 탐색은 자리를 옮기지 않는 명령으로 두고
그 자리에서 속을 따로 돌려 봅니다(`493-497`, `635-638`). 수량자로 메모리를 태우지 않도록 명령 수 상한
5000을 둡니다(`430-431`, `460-466`).
**근거**: `(가+)+나`를 되추적으로 짜면 24글자에 6초가 걸렸다는 측정이 적혀 있고(`poe-regex.js:416-417`,
`README.md:278-283`), 같은 패턴이 1초 안에 끝나야 한다는 회귀 테스트로 남아 있습니다
(`test/poe-regex.test.js:263-270`). 가능한 이유도 적혀 있습니다 — 역참조를 받지 않으므로 패턴이 언제나
정규 언어이고, 시간이 글자 수 × 명령 수에 비례합니다(`418-420`).
**결과**: 역참조는 앞으로도 지원할 수 없습니다(NFA로 표현 불가) — ADR-008이 역참조를 `unsupported`로 막은
것과 서로를 지탱합니다. 수량자는 컴파일 시점에 펼쳐지므로(`531-558`) `{1,100000}` 같은 표기는 상한에 걸려
오류가 됩니다. 게임 자체는 되추적이라 `((.*)*)`에서 실제로 멈추지만, 확장은 그 지점에서 의도적으로 다르게
동작합니다.
**대안**: 되추적 + 시간 제한(결과가 입력·기기에 따라 달라짐), 입력 정규식의 길이·형태 제한(호환 상실).

## ADR-010. 정규식 키워드는 한글 3글자 이상으로 정하고, 목록 밖까지 대조해 검증한다

**상태**: 채택 (구현됨)
**요구사항**: FR-REGEX-01·02·09, FR-DATA-01·02·03·04·05, NFR-DEV-03·04
**맥락**: 인게임 검색은 모드 문구가 아니라 **아이템 전문**을 훑습니다 — 아이템 이름, `아이템 종류: 지도`
같은 속성 줄, 목록에 없는 모드, 고급 모드 설명 줄까지 대상입니다. 키워드가 그 어딘가에 걸리면 그 모드가
없는 지도까지 사라집니다.
**결정**: 키워드는 그 모드에만 걸리는 최단 부분문자열로 하되 **한글 3글자 이상**으로 씁니다
(`map-mods.js:12-15`). 공백은 `.`으로 쓰고 굴림마다 바뀌는 숫자는 넣지 않습니다. 유일성은 목록끼리 맞춰
보는 데서 그치지 않고 목록 밖 자료까지 함께 대조해 검증합니다 — 어떤 자료를 어느 방향으로 대는지는
[DESIGN.md](../DESIGN.md) §8에 있습니다.
**근거**: 결정의 두 축입니다. **왜 하필 3글자인가** — 희귀 지도에는 무작위로 만든 이름('운명의 도전' 같은)이
붙는데 그 낱말 목록을 구할 수 없어 검사로 막지 못하고, 2글자는 그런 이름에 걸릴 확률이 무시할 수준이
아닙니다. 길이는 문제되지 않습니다. 12개를 골라도 58자로 인게임 한도 250자의 4분의 1입니다
(`map-mods.js:12-15`, `test/trade-query.test.js:364`, `:375`). **왜 목록끼리 대조만으로는 부족한가** —
인게임 검색이 보는 것은 목록이 아니라 아이템 전문이라, 목록 안이 깨끗해도 밖에서 걸립니다. `억제`는 목록
문구에 빠진 줄이 있어 목록끼리 맞춰서는 충돌이 드러나지 않았고, `변덕`은 모드 문구가 아니라
`{ 접두어 속성 부여 "변덕스러운" … }`이라는 고급 모드 설명 줄에 걸렸습니다(`test/trade-query.test.js:190-222`).
방향이 다른 사고도 있습니다 — stat id를 틀리면 거래소는 걸러 주지 않는데 인게임 필터만 숨기므로 id도 거래소
stats에 대고 확인합니다(`:224-233`). 타락으로 붙는 모드는 `explicit`이 아니라 `implicit`입니다
(`map-mods.js:23`). 데이터 출처는 poedb(https://poedb.tw/kr/Maps_top_tier)와 거래소 stats API
(https://poe.kakaogames.com/api/trade/data/stats)이고, 키워드 문법 규칙은 https://poeregexkr.web.app/
입니다(`map-mods.js:4-7`).
**결과**: 키워드를 짧게 만들 자유가 없어졌습니다 — 정규식이 길어지는 대신 오작동 확률을 낮추는 쪽입니다.
리그가 바뀌면 `test/fixtures/`를 다시 받고 `data/`의 원본에서 대조표를 다시 뽑아야 합니다(FR-DATA-05). 검증
데이터는 실행에 쓰지 않고 테스트에서만 읽으며(NFR-DEV-04), 현재 `node --test`는 60개 통과입니다.
`map-mods.js:19-20`의 헤더 주석은 아직 "다섯 방향"이라 적혀 있어 코드보다 뒤처져 있습니다(실제 일곱 방향).
**대안**: 모드 문구 전체를 키워드로(250자 한도 초과), 2글자 허용(무작위 이름에 걸림), 목록끼리만 대조(`억제` 사고).

## ADR-011. 영향력 지도 제외는 필터가 아니라 implicit stat id 8종을 직접 나열해서 한다

**상태**: 채택 (구현됨)
**요구사항**: FR-BUILD-01·02·03·04·05·07, NFR-API-01
**맥락**: 8모드 검색에 영향력 받은 지도가 섞이면 안 되는데, 거래소 필터 목록에는 영향력 항목이 아예 없고 pseudo
영향력 스탯은 지도에 걸리지 않습니다 — 지도 매물에는 `influences` 속성이 없고 implicit 모드로만 표시됩니다.
**결정**: implicit stat id 8종(쉐이퍼·엘더·정복자 4종·전체·태초자의 기억)을 `not` 그룹으로 직접 뺍니다
(`trade-query.js:12-28`, `56-64`). 같은 쿼리에서 희귀도는 `nonunique`, 거래 옵션은 `securable`, 지도 등급은
`min=max=16`, `# 속성 부여`는 8개 이상, 정렬은 가격 오름차순입니다(`30-41`, `66-82`). 조건은 URL로 넘길 수
없으므로 `POST /api/trade/search/<리그>`로 등록하고 돌아온 id로 결과 주소를 만듭니다(`4-6`,
`panel.js:923-955`).
**근거**: 필터에 영향력 항목이 없고 pseudo 스탯이 지도에 안 걸린다는 관찰이 주석에 있습니다
(`trade-query.js:14-17`). 쓰는 id는 전부 거래소 stats에 있는지 검사하고(`test/trade-query.test.js:276-280`),
`nonunique`는 거래소가 준 필터 정의의 '모든 비고유' id와 같은지 대조합니다(`data/search-filters.json`,
`:395-411`) — 희귀도를 비우면 모드가 정해진 고유 지도가 섞이기 때문입니다. `securable`은 귓속말을 기다리는
직접 거래 매물을 빼기 위한 것이고, POST를 쓰는 이유는 거래소 번들에 `location.search` 처리가 없다는
관찰입니다(`trade-query.js:4-6`, `39-41`).
**결과**: 영향력 종류가 늘거나 id가 바뀌면 `INFLUENCE_IDS`를 손으로 고쳐야 하고, 고치면
`test/fixtures/trade-stats.json`에도 그 id가 있어야 테스트가 통과합니다. 검색 등록이 요청이므로 버튼에 2.5초
최소 간격을 두고 429는 `Retry-After`를 그대로 안내하며(`panel.js:722-723`, `905-911`, `930-934`), 등록 후
이동에는 `pending`이 필요합니다(ADR-006). 결과가 실제로 깨끗한지는 수용 기준 A9로 남아 있습니다.
**대안**: 영향력 체크박스 필터(목록에 없음), pseudo 스탯(지도에 안 걸림), 확장이 결과를 걸러 내기(NFR-API-05와 충돌).

## ADR-012. 빌드 도구·의존성·모듈 시스템을 두지 않고, 로드 순서를 의존 그래프로 쓴다

**상태**: 채택 (구현됨)
**요구사항**: NFR-DEV-01·02·05, NFR-SEC-05
**맥락**: 확장은 압축 해제된 형태로 로드하고, 콘텐츠 스크립트는 `manifest.json`이 정한 순서대로 로드되어 하나의
스코프를 나눠 씁니다. 번들러를 얹으면 산출물과 원본이 갈라지고, 테스트에는 러너 같은 의존이 따라옵니다.
**결정**: 번들러도 `package.json`도 `node_modules`도 두지 않습니다. 각 파일은 전역 함수를 정의하고, 테스트에서만
쓰이도록 파일 끝에 `if (typeof module !== 'undefined') module.exports = …`를 답니다(`poe-regex.js:779-791`,
`search-summary.js:188-196`, `trade-query.js:171-184`). 테스트는 `node --test`만 쓰고, 브라우저에서
`manifest.json`이 하던 일(전역을 순서대로 깔아 두기)을 테스트가 대신 합니다(`test/trade-query.test.js:6-17`).
검증 데이터는 JSON으로 둡니다 — `node --test`가 `test/` 아래 `.js`를 전부 테스트 파일로 잡기 때문입니다.
**근거**: 러너는 노드에 들어 있는 `node:test`뿐이라 받아 올 것이 없습니다(`test/poe-regex.test.js:5-8`). 전역
공유가 전제이므로 이름 충돌을 피해야 하는 파일은 통째로 IIFE에 넣습니다(`copy-en.js:10-13`). `manifest.json`의
`js` 순서가 곧 의존 방향이고, 그 사슬은 [DESIGN.md](../DESIGN.md) §4에 있습니다. 예를 들어
`trade-query.js:47`이 `POE_QUERY_MAX`를 그대로 참조하고, 두 값이 같은지도 테스트가 봅니다
(`test/trade-query.test.js:382-384`).
**결과**: 파일을 새로 만들면 `manifest.json`의 `js` 목록에 **순서에 맞게** 넣어야 하며, 빠뜨리면 브라우저에서만
조용히 깨집니다(NFR-DEV-02). 전역 이름이 하나의 이름 공간이라 충돌을 직접 살펴야 하고, TypeScript·최소화는
포기했습니다(NFR-DEV-05). 그리고 호스트 목록이 `manifest.json`과 `trade-url.js:16-29`의 `TRADE_HOSTS`로
갈라지므로, 사이트를 추가할 때 여러 곳을 손으로 맞춰야 하는 NFR-SEC-05를 이 결정의 대가로 떠안습니다
(`trade-url.js:14`). 실제 절차는 [DESIGN.md](../DESIGN.md) §9에 있습니다.
**대안**: ES 모듈 + `import`(번들 단계 필요), 번들러 도입(산출물과 원본이 갈라짐), 테스트 프레임워크(의존성).
